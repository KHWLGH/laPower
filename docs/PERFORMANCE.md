# 性能基准与边界

本文记录可重复的算法、存储、启动和发货形状基准。它用于评估性能优化，不把浏览器帧率或真机长跑当作每次改动的自动回归。

## 测量范围

| 基准 | 命令 | 关注点 |
| --- | --- | --- |
| 核心算法 | `node bench/core.mjs` | 列存储、分桶、范围统计、能量积分 |
| 算法阶段对照 | `node bench/phase2.mjs` | 范围统计和协作切片的前后版本对照 |
| 存储阶段对照 | `node bench/phase3.mjs` | 分块存储、统计和能量计算的前后版本对照 |
| 长期记录内存 | `npm run bench:memory` | 常量块共享、流式 CSV 导入、追加快照及清空后的缓冲释放 |
| 算法对照 | `node bench/extrema.mjs` | 逐样本扫描与极值索引 |
| 启动 | `node bench/startup.mjs` | 原生二进制启动分段和资源形状 |
| 发货形状 | `node bench/packaging.mjs` | `out/` 文件集合、阻塞资源和孤儿资产 |
| Rust | `cargo bench -p lapower` | 协议解码、编码、选择路径 |

`bench/core.mjs --compare` 使用 `bench/baselines/` 中的输入指纹和指标集合进行多轮对照；`--verify-baseline` 只运行一次数据正确性检查，并校验输入指纹、指标集合、重复次数和轮次设置，不执行预热、性能计时或计时阈值判断，适合 CI。共享 runner 的绝对耗时会受频率、负载和缓存影响，单次耗时只作为报告，不直接升级为发布门禁。

## 前端产物

`npm run build` 将 `src/` 镜像到 `out/`，并在 `out/` 内合并阻塞样式表；开发模式保留原生 JavaScript 模块。`npm run build:dist` 的发布模式进一步把应用入口、两个 CSV Worker、PD 导出 Worker 和范围统计 Worker 分别合并，保留 Worker 文件名并移除已合并的模块。`node scripts/build-dist.mjs --bundle-js` 可生成未压缩的合并版本，用于启动对照。typecheck 与 Node 核心测试继续使用 `src/` 中的源模块。`bench/packaging.mjs` 检查：

- `out/` 中从源码镜像的文件都已跟踪；合并脚本、样式与从 `src-tauri/icons/` 复制的关于页图标由构建生成；
- 声明文件和点号目录不会进入发货集合；
- `index.html` 不含内联脚本，资源引用可以解析；
- 没有新的已跟踪孤儿资产。

这些是确定性发货不变量，适合固定在 `perf-shape` CI job 中。

## 存储与数据完整性

### 常量块共享与导入分配

在 Windows / Node 的独立进程中比较修改前源码与当前源码，测试数据采用固定 1 ms 间隔、无温度、五个记录段，其他信号通道逐点变化。持续追加同时保留导出快照，随后补入 4097 个点。以下列缓冲按独立 `ArrayBuffer` 计数；RSS 为每块处理后的进程抽样峰值，两种指标不能互相替代。

| 场景 | 原始点数 | 列缓冲节省 | 修改前 / 后 RSS 峰值（MiB） |
| --- | ---: | ---: | ---: |
| 持续追加 | 1,000,000 | 24.5% | 150.0 / 127.0 |
| 流式 CSV 导入 | 1,000,000 | 24.5% | 255.3 / 230.8 |
| 持续追加 | 5,000,000 | 24.9% | 523.8 / 409.0 |
| 流式 CSV 导入 | 5,000,000 | 24.9% | 747.4 / 595.2 |

所有列的 SHA-256 前后一致，清空并完成 GC 后数据缓冲回到初始水平；三次替换后缓冲量保持稳定。这里未测量 Tauri / WebView2 / GPU 整个进程树，节省比例也取决于实际常量通道数量；记录容量上限继续使用原有保守估算。

完整常量块在同一列内共享，只保留最近一个常量块作为复用候选；可追加尾块独占缓冲。写入历史值和导入补值都复制需要修改的块，Worker 转移时对共享缓冲去重。固定快照、CSV 数值、统计、积分和图表极值保持一致。

分块列存储以 4096 点为块，避免连续数组扩容时整列复制。性能评估应同时记录范围统计、能量积分、追加边界和容量变化，并用现有 `chart-*`、`range-stats`、`recording` 和 `recording-spool` 核心测试确认结果不变。

每点保存实际采样间隔；CSV 在末尾追加可选的 `SampleInterval(ms)`，混合采样率按逐点间隔判定积分空档。旧文件继续使用摘要间隔、时间序列估算和绝对 2 秒保护。12 列原始数据与辅助索引按约 112 字节/点估算，CSV 按约 128 字节/行估算。

恢复文件的表头立即同步，Rust 每秒刷新缓冲并唤醒前端排空、回写表头；大回填每轮只捕获一次固定快照，写入途中也检查同步期限。失败时保留恢复文件；仅成功同步的正常收尾删除它。扫描兼容历史碰撞名称 `stem.partial-2.csv`。

密集跟随投影允许自然追加期间完成固定快照，按该快照的 X 范围提交，再处理最新窗口；隐藏监控页时取消准备。大范围统计使用 Worker 按原顺序折叠，每次转移最多 4096 行的副本；同一窗口最多一个活动任务，计算启动间隔为 `max(250 ms, 上次完整计算耗时 × 4)`。更新期间显示已完成范围及其边界，Worker 不可用时回退到协作分片。PD 导出每批最多 128 条报文，在 Worker 中格式化并按写入确认推进，单块最多 1 MiB，保持 v2 文件和 v1 元数据兼容。

CSV、采集、录制和协议解析的性能优化优先复用现有核心测试与基准。只有发现数据损坏、协议不兼容、崩溃/死锁或已确认的高影响回归时，才新增针对性测试或基准。

## 密集图表显示预算

每桶、每通道保留首点、末点和最早的最小／最大值下标，按源下标排序去重，读取真实时间，重复时间不偏移。候选点之间只有原始区间全部为有限值时才连线；描边与填充共用这些几何，功率导航图保留原预算。完全放大也统一使用线性连接。

极值索引每页 256 节点，每节点保存八通道的最小／最大下标和有限值数量，24 KiB／页；数值读取原始列。360 万点索引缓冲为 21,823,488 B，追加不复制历史页。录制时以 1 ms 协作预算、每步最多 1024 个原始样本追赶固定前缀，交互优先，已完成前缀继续复用。冷暂停优先复用同源、同范围的完整录制投影，仅同步补齐至多 4096 点尾部；后台完成后一次原子升级。窗口、源、录制状态或可见性变化会取消过期升级。时间预算在步间检查，不是单任务耗时的硬上限。

原始列始终完整保留。自动录制显示默认每 2 个 CSS 像素一个 min/max 桶，内部档位为 1、2、4、8、16 像素；回看固定以一个画布设备像素为桶预算单位，不因慢帧放宽到粗桶。桶预算至少 64，样本数/桶取 2 的幂，实际条带宽度可能接近两个预算单位；合并和同密度重建逐值一致，包括 NaN、正负零和未满尾桶。回看放大到点数不超过绘图区设备像素宽度的 4 倍、且不超过 16384 点、曲线往返复杂度在固定预算内时恢复原始点及裁剪邻点，自动录制的原始点阈值仍为 CSS 宽度；光标始终查原始样本。实际 DPI 取当前画布后备宽度与 CSS 宽度的比值，而非可能已经改变的系统缩放值。

导航缩略图同样使用每 2 个 CSS 像素一个桶的固定预算，避免主图降密度后，缩略图仍提交过多顶点。其预算从约 4 个顶点/CSS 像素降为约 1 个；单点功率峰值与未满尾桶的最新时间保留，并由绑定回归测试验证。

显示分桶与阴影保护采用独立规则，面积填充默认保留。达到 4 点/CSS 像素才有关闭阴影的资格（600 CSS px 至少约 2400 点），达到资格仍不会自动关闭。录制中普通慢帧先确认并降低显示密度，实际绘制过降低后的密度、又出现连续两次慢帧，才关闭阴影；回看保持设备像素级预算，连续两次慢帧可关闭阴影。单次超过 100 ms 的严重绘制延迟允许直接关闭。每次刷新新增点数超过 4×绘图区宽度只标识大批次压力，健康批次不会关闭阴影。这些规则不按请求采样率或累计时长设置硬开关。密度及阴影反馈均只计算实际绘制耗时和绘制后的帧延迟，排除导入、列初始化和协作冷建在绘制前的耗时。

恢复阴影需要连续两秒健康绘制，并距离上次关闭至少五秒，以免频繁闪烁。页面隐藏、数据源替换、窗口低于阴影候选阈值或用户调整填充/通道显隐时清除保护。独立密集窗口切换清除旧计时证据、保留已经确认的填充保护；同一数据源的录制切到回看可沿用填充压力，但不沿用录制密度。同一次连续拖动及实时全历史/跟随窗口的自然追加保留有效证据。用户设置为 0 的通道始终关闭填充；静止回看不为累计恢复时间创建无限重绘。拖动与松手在同一分辨率下采用相同投影规则。

密集曲线直接按设备像素列计算有序线段覆盖范围，先合并重叠区间再写入画布大小的透明 RGBA 位图，跳过随后会被丢弃的标准路径构造。各通道使用独立、有界的候选点缓冲；uPlot 的共享数组只承载坐标和光标。填充沿相同有序线段形成独立区域，保持基线、通道叠放与现有填充保护。关闭填充时合并通道并一次上传；填充开启时按通道先填充再描边。缺测区间两侧不合成连接。OffscreenCanvas 不可用或通道颜色／透明度不适用时，用相同几何生成 Canvas 路径。原始点复制范围和往返复杂度保护继续保留，光标仍查询原始样本。

极值索引按数据源已完成的前缀复用：缩小右端或向较早位置平移仅查询索引，不把窗口变短当成原始列截断。新增点只补建索引尾部，清空、替换及修改源数据使索引失效。已有索引的投影按每步最多 32 个桶查询计量，原始扫描每步最多 4096 点；先在约 4 ms 的预算内尝试完成，完成即可在请求帧提交，剩余工作协作分片。历史冷建每步最多 4096 点、每片约 1.5 ms。仅完整投影可发布，过期窗口投影取消后仍保留有效的历史索引。

`drawClear` 到 `draw` 只反映 JS 绘制耗时，不能代表 Canvas 栅格化结束。诊断同时保留 `draw` 到下一次 rAF 的延迟，以及请求以来的实际帧间隔；显示策略只依据绘制及绘制后的压力。空闲基线取最近 32 个候选帧间隔的第 20 百分位，排除包含图表绘制的帧。录制中超过 `max(33 ms, 空闲帧间隔 × 2)` 两次降一档，单次超过 100 ms 降两档；稳定两秒后尝试恢复，每五秒最多恢复一次。回看不降密度。密集实时、静止回看及尚未确认健康的填充交互最多观察三个后续 rAF；未知填充交互在观察完成前合并最新窗口，避免多条昂贵路径排队。确认健康或关闭填充后，连续交互逐帧消费反馈，松手直接提交最终位置。首次普通慢帧可排一次填充确认重绘，健康反馈结束任务，不建立无限恢复循环。

绘图请求区分 `live`、`interaction` 和 `maintenance`。实际采样间隔为 1 ms 时，自动绘图在 50–100 ms 间调节；100 Hz 的健康绘图不因可见点数较多而设置固定刷新间隔。交互会打断待执行的实时限帧计时器，按 rAF 合并最新窗口；显示设置及反馈重绘同样绕过采样限帧。实际采样间隔读取记录尾部的 `sampleIntervals`，没有有效值时使用当前设置；这些策略不参与采样、保存、统计或积分。

`window.__WITRN_PERF__()` 的 `charts.main.last` 包含 `sourcePointCount`、`displayPointCount`、`pixelsPerBucket`、`displayDense`、`fillSuppressed`、`fillSuppressionReason`、`recentAppendCount`、`refreshSource`、`refreshIntervalMs`、`drawMs`、`nextFrameDelayMs` 和 `frameDelayMs`。其中 `nextFrameDelayMs` 是第一次后续 rAF 的延迟，`frameDelayMs` 还包含请求以来的实际帧间隔；历史仍以 512 项为上限。`refreshIntervalMs` 为该请求的自动绘图间隔，交互与维护请求为 0。`fillSuppressionReason` 为 `severe-frame`、`persistent-slow-frame` 或 `large-batch-slow-frame`，未抑制时为 null；`recentAppendCount` 从上次主图提交计数，导入或预载历史不计作实时新批次。这些指标只参与显示调节，不影响采样、CSV、统计或能量积分。

## 测量与硬件边界

性能比较应固定构建、主机、窗口、DPI、通道数、采样率、时间戳分布和填充设置，并区分录制、热暂停、冷暂停和连续交互。公开填充设置使用百分数，例如 12% 传入 `12`，只对电压、电流、功率和温度四路启用；早期误传 `0.12` 并额外填充其他通道的计时不能用来证明正常界面 12% 填充的性能。

JS `draw` 回调、下一次 rAF 和显示器实际呈现不是同一指标。应分别记录完整窗口首图、最终精细图、准备 CPU、绘制及后续帧延迟、最长无曲线更新时间；暂停 Promise 只等待原生尾点栅栏，不等待图表呈现或磁盘同步。本机观察目标为帧间隔 p95 ≤33 ms、交互响应 p95 ≤50 ms，极端八通道交变信号仍可能超出目标；p95 达标也不代表每一帧达标。

历史 KM003C 对照从 1,434,583 点实测历史恢复后继续采集，不能视为重新不中断采集同等点数。有效数据只有七路且温度缺测，接线为低电平信号；真实 360 万点不中断采集、有效温度、受控负载强交变和断电恢复仍需实机检查。曾出现仪表队列序号空洞及时间未递增保护，显示优化没有消除这些采集端异常。

浏览器合成矩阵和短时 WebView2 测量不能代替当前版本的持续实机录制。真机检查应保持桌面解锁、窗口前台可见，分别持续录制 100/1000 次每秒至少五分钟，记录实际采样率、原始点数、序号异常、尾点完整性和交互延迟。`document.hidden` 或焦点状态不能单独证明窗口可见；历史版本的测量也不保证当前构建及所有机器表现相同。绝对耗时只适合同机对照，不作为共享 CI 门槛。

## 启动测量限制

`bench/startup.mjs` 的绝对毫秒只适合在同一批次、相同构建和相近主机状态下比较。记录结果时保留运行环境和主机探测值，避免把一次启动读数解释成跨平台保证。启动 benchmark 按需手动运行，不作为浏览器自动回归。

前端标记分别记录 `uiReady`（设置及平台信息生效、页面初始化完成）、`listenersReady`（采集及协议监听完整注册）、`devicesScanned` 和 `recoveriesScanned`。`appReady` 仍需页面、关闭监听、设备监听和设备扫描全部完成，不以提前挪动完成标记表示启动加速。监听失败时保持连接按钮禁用；异常记录扫描不阻塞 `appReady`。

## CI 与手动验证

CI 固定运行 `bench/packaging.mjs`、`bench/core.mjs --verify-baseline` 和报告型算法/Rust benchmark。性能优化开发者可按需运行：

```bash
npm run build
node bench/packaging.mjs
node bench/core.mjs --verify-baseline --output bench/results/verify.json
node bench/core.mjs --compare
node bench/phase2.mjs
node bench/phase3.mjs
node bench/extrema.mjs
node bench/startup.mjs
cargo bench -p lapower
```

真机检查仍可由维护者在目标设备上手动执行，但不属于托管 CI 的固定回归链路。详细的测试新增规则见 [开发与构建：测试与回归边界](DEVELOPMENT.md#测试与回归边界)。
